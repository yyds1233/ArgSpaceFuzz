# concurrent_oracle 模块代码审查与修改建议

> 适用仓库：[ArgSpaceFuzz](https://github.com/yyds1233/ArgSpaceFuzz)  
> 审查对象：`concurrent_oracle/`  
> 文档性质：基于当前公开源码逻辑的静态审查建议  
> 目标：优先修复可能导致 Oracle 漏报、误报或实验结论不准确的问题，不推翻现有总体架构。

## 1. 总体结论

当前 `concurrent_oracle` 已具备可运行的基础流水线，包含 Harness 分析与转换、适用性分析、执行器、O1–O7 Oracle、结果记录和验证方案。整体架构无需重做，下一阶段应从“补充模块”转向“验证 Oracle 判定的正确性”。

建议优先处理三个 P0 问题：

1. Tensor 摘要不能可靠区分不同内容，可能导致语义差异漏报。
2. 实例方法 API（如 `torch.Tensor.add_`）的解析与捕获可能不完整。
3. O1 安全 Oracle 可能将部分成功拒绝误判为整体通过。

之后再处理线程数扫描、复现率统计、上下文生命周期和 LLM 转换等问题。

**审查范围说明：** 本文整理的是源码静态审查中识别出的风险与建议，并非已在本地运行测试后确认的全部缺陷。每项修改都应通过针对性的回归测试验证。

## 2. P0：优先修复的问题

### 2.1 Tensor 摘要不能作为可靠的正确性证据

**涉及位置：**

- `templates/concurrent_harness.py`
- `_digest()` 及使用其结果的 Oracle

**当前风险：**

当前 Tensor 摘要主要记录 `dtype`、`shape`、`numel` 和数值总和；复数 Tensor 使用绝对值总和。不同 Tensor 可能具有相同的摘要。例如：

```python
torch.tensor([1, 2])
torch.tensor([0, 3])
```

两者形状、类型、元素数量和元素总和相同，但内容不同。如果 Oracle 只比较这类摘要，就可能漏掉输出差异或状态变化。

**修改建议：**

1. 对 Tensor 保存完整的规范化内容，或使用能覆盖实际内容的哈希。
2. 对需要浮点容差比较的 Oracle，保留可比较的实际值，不能只比较哈希。
3. 明确处理 NaN、Inf、复数、稀疏 Tensor 等特殊情况。
4. 摘要可以继续用于日志展示，但不能单独作为正确性判定证据。
5. 对大 Tensor 可以采用“内容哈希 + 必要时保留完整内容”的分层策略，同时记录 dtype、shape、layout、device 等元信息。

**建议增加的回归测试：**

- 相同 shape、dtype、numel 和元素总和，但内容不同的 Tensor 必须能被识别。
- 内容完全相同的 Tensor 应得到相同内容摘要。
- NaN、Inf、复数和空 Tensor 的处理结果应明确且稳定。
- 浮点容差比较与精确内容比较应是不同的判定模式。

**验收标准：** 不再依赖元素总和等有碰撞可能的摘要来判定 Tensor 是否相同；各 Oracle 使用与其语义相符的比较方式。

### 2.2 补齐实例方法 API 的解析与调用捕获

**涉及位置：**

- `harness_analyzer.py`
- `case_capture.py`
- `templates/concurrent_harness.py`

**当前风险：**

目标 API 解析主要依赖模块路径和属性名。对于 `torch.Tensor.add_`，若把 `torch.Tensor` 当作普通模块路径处理，可能无法正确解析；而 Harness 中常见的 `x.add_(...)` 是接收者为变量的实例方法调用，单凭 `torch.xxx` 形式的完整路径也无法可靠识别。

导入别名也可能影响捕获，例如：

```python
from torch import addmm as my_addmm
```

如果调用拦截只匹配原始名称或特定属性路径，别名调用可能绕过捕获。

**修改建议：**

1. 区分模块函数、类方法和实例方法三类 API。
2. 支持 `x.add_(...)` 等实例方法调用点识别。
3. 结合目标方法名、接收者类型线索、导入语句和别名映射进行解析。
4. 在可行范围内静态解析导入别名；不能可靠解析时，明确标记为不确定，而不是假定已捕获。
5. 对运行时 monkey-patch 或包装器增加有效性检查，确认目标调用确实进入捕获逻辑。
6. 当目标调用次数为零时，应区分“输入没有触发调用”和“拦截器未能捕获调用”。

**建议增加的回归测试：**

- 模块函数调用。
- `from torch import ...` 形式的导入。
- 导入别名调用。
- Tensor 实例方法调用，如 `x.add_(...)`。
- 同名但属于其他对象的方法调用，避免误捕获。
- 目标调用没有发生与目标调用未被拦截两种情况的区分。

**验收标准：** 对支持的 API 形式，能确认目标调用被捕获；无法确认时返回明确的诊断状态，不将其当成正常通过。

### 2.3 修复 O1 安全 Oracle 的逐项判定逻辑

**涉及位置：**

- `oracles/safety.py`
- `evaluate()`

**当前风险：**

当前实现可能把基线与并发观测中的异常汇总，只要出现预期异常类型，就返回 `PASS`。若一个配置正确拒绝非法输入，另一个配置却没有拒绝，汇总结果仍可能掩盖失败。

此外，把 `RuntimeError`、`ValueError` 等异常类型统一视为预期拒绝类型过于宽泛。异常类型本身不能证明输入已按照 API 合同被正确拒绝。

**修改建议：**

1. 为每个非法输入定义明确的预期行为，例如应拒绝、应返回特定结果，或该输入超出测试范围。
2. 按 case、执行配置和 trial 分别判定，不要先把所有异常合并后再作结论。
3. 只有所有必需观测都符合合同，才能汇总为 `PASS`。
4. 若某些配置没有拒绝、观测缺失或发生无法归因的异常，应根据证据返回 `VIOLATION` 或 `INCONCLUSIVE`。
5. 维护预期异常的具体类型、条件和来源；不要仅凭宽泛异常类型列表判断安全拒绝。
6. 区分“正确拒绝非法输入”“意外异常”“进程崩溃”“超时”和“返回了不应接受的结果”。

**建议增加的回归测试：**

- 所有配置都按合同拒绝非法输入，应返回 `PASS`。
- 一个配置拒绝、另一个配置接受非法输入，不得返回整体 `PASS`。
- 抛出不符合合同的异常时，不得仅因异常类型属于 `Exception` 子类就判为 `PASS`。
- 观测缺失、超时或崩溃时，应按明确规则返回结果。
- 对预期行为未定义的输入，返回 `INCONCLUSIVE` 或 `NOT_APPLICABLE`，而不是猜测其结果。

**验收标准：** O1 的汇总结果不会掩盖单个配置或 case 的失败；每个结论都能追溯到对应合同和观测。

## 3. P1：重要的结果正确性与评估问题

### 3.1 让 `--threads` 真正执行所有线程配置

**涉及位置：**

- `runner.py`
- `run_plan()`

**当前风险：**

当前实现使用 `max(external_threads)` 选择一个线程数。如果传入 `--threads 2,4,8,16`，可能只运行 16 线程配置，而不是完成四组扫描。

**修改建议：**

1. 遍历所有 `external_threads` 配置。
2. 每个线程数分别生成执行记录和 Oracle 结果。
3. 把线程数、trial 数、锁配置、内部线程数等信息写入结果。
4. 汇总报告应同时展示每种配置的结果和整体结果。
5. 某个配置执行失败，不应导致其他配置的结果被覆盖或丢失。

**验收标准：** 输入四个线程数时，报告能清楚证明四种配置均已执行，并且各自有独立的统计数据。

### 3.2 拆分复现率指标

**涉及位置：**

- `cli.py`
- `cmd_reproduce()`

**当前风险：**

若将 `VIOLATION` 和 `INCONCLUSIVE` 都计入 `reproduction_rate`，则重复出现不确定现象也会被报告为缺陷复现。

**修改建议：**

分别统计：

- **违规复现率：** 重复执行中出现 `VIOLATION` 的比例。
- **候选现象复现率：** 重复执行中出现目标异常或结果差异的比例，可包含尚未确认的现象。
- **确认复现率：** 经合同核实、必要的人工确认后，确认缺陷重复触发的比例。

报告必须明确各项指标的分子、分母、重复次数和统计条件。`INCONCLUSIVE` 不能直接算作已确认缺陷。

**验收标准：** 即使所有 trial 都返回 `INCONCLUSIVE`，违规复现率也不能因此被报告为 100%。

### 3.3 强化 O6 上下文生命周期检查

**涉及位置：**

- `templates/concurrent_harness.py`
- `oracles/context.py`

**当前风险：**

当前 grad-mode 探针能够观察部分线程状态，但如果没有完整检查上下文进入、退出和恢复，就不能据此推断整个生命周期都正确。

**修改建议：**

将上下文测试拆成两个子场景：

1. **线程隔离：** 一个线程改变状态，另一个线程的状态应符合对应的线程隔离语义。
2. **上下文恢复：** 记录进入前状态，验证进入后状态，退出后再次检查恢复情况，并检查主线程是否受到影响。

对于 `torch.random.fork_rng` 等 RNG 相关场景，应独立验证随机状态的作用范围和退出后的恢复行为。不要将 grad-mode 的测试结果直接外推到所有上下文类型。

**验收标准：** 报告明确区分线程隔离测试和生命周期恢复测试，并记录每个阶段的观测。

### 3.4 避免超时或崩溃后的不完整观测造成误判

**涉及位置：**

- `templates/concurrent_harness.py`
- `runner.py`
- `oracle_engine.py`

**当前风险：**

线程等待超时后，部分线程可能仍在运行，共享状态也可能继续变化。若此时直接将中间状态与串行基线比较，可能错误地将不完整观测判定为语义违规。

**修改建议：**

1. 为观测增加完整性状态，例如 `complete`、`partial`、`missing`。
2. 将执行状态与 Oracle 状态分开保存。
3. 当出现 `TIMEOUT`、`CRASH` 或 `ERROR` 时，默认不使用不完整输出差异直接判定 O2/O3 为 `VIOLATION`。
4. 若测试本身就是检测崩溃或超时，则由相应 Oracle 根据明确的测试性质判定。
5. 对不完整观测返回 `INCONCLUSIVE`，并保留退出码、日志、线程状态和崩溃证据。

**验收标准：** Oracle 不会把未完成的执行结果当作完整结果；针对崩溃和超时的专用测试仍然能够报告相应现象。

## 4. P1：适用性分析需要保留规则与 LLM 的差异

**涉及位置：**

- `llm_suitability.py`
- `api_suitability_analyzer.py`

**当前风险：**

如果 LLM 的非空 `candidate_oracles` 直接替换规则候选，模型分析不完整时就可能删除规则引擎已经发现的测试方向。若 `evidence` 字段没有保存到最终报告，也会降低结果可追溯性。

**修改建议：**

1. 分别保存 `rule_candidates` 和 `llm_candidates`。
2. 在初期使用候选并集，或要求 LLM 为删除的候选给出理由。
3. 保存 LLM 输出的 `evidence`，至少包含来源类型、文件路径或文档位置、判断理由。
4. 对被 LLM 降级的 API 抽样执行，统计适用性漏报。
5. 不把 LLM 的置信度解释为漏洞概率。
6. 对无法从代码或文档证实的结论标注为推测或待核实。

**验收标准：** 可以对比规则和 LLM 的判断差异，追踪候选为何被保留或降级，并能估算适用性分析的漏报风险。

## 5. P2：后续再接入 LLM 并发 Harness 转换

**涉及位置：**

- `pipeline.py`
- `transformer.py`
- `llm_transformer.py`（建议新增或完善）

当前转换流程以确定性模板为主，LLM 转换尚未接入主路径。这不是当前必须修复的缺陷，也不建议为了使用 LLM 而让模型自由改写所有 Harness。

**建议路线：**

1. 继续保留确定性模板作为默认路径。
2. 将 LLM 转换设计为可选后端。
3. 输入原始 Harness、测试计划、Oracle 规范和固定接口约束。
4. 生成后必须经过语法与依赖检查、串行基线和并发正控测试。
5. 与模板方案比较首次生成成功率、修复后成功率、串行基线通过率、Oracle 正控检出率和执行成本。
6. 对不满足固定接口的生成结果进行有限修复；仍失败则记录失败原因，不得将其计入有效执行样本。

**验收标准：** LLM 转换能够在固定接口和验证门槛下运行，并且有实验数据证明它带来了额外价值。

## 7. 建议的修改顺序与验收标准

| 优先级 | 修改项 | 最低验收条件 |
| --- | --- | --- |
| P0  | Tensor 比较 | 相同摘要但内容不同的 Tensor 不会被误认为相同 |
| P0  | 实例方法与别名捕获 | 支持的调用形式均能被捕获；捕获失败可诊断 |
| P0  | O1 逐项判定 | 部分配置失败时不会被汇总成整体 `PASS` |
| P1  | 线程数扫描 | 所有指定线程配置均实际执行并独立记录 |
| P1  | 复现率指标 | `VIOLATION` 与 `INCONCLUSIVE` 分开统计 |
| P1  | O6 生命周期 | 线程隔离与退出恢复分别有测试 |
| P1  | 不完整观测保护 | 超时、崩溃和部分结果不会直接造成不可靠的语义判定 |
| P1  | LLM 适用性可追溯 | 规则候选、LLM 候选及证据均保留 |
| P2  | LLM 转换 | 与模板方案完成可量化的对照评估 |

## 8. 最终建议

建议先集中修复三个 P0 项目：**Tensor 内容比较、实例方法调用捕获、O1 逐项判定**。这三项直接影响 Oracle 能否正确发现问题。

随后修复线程数扫描、复现率和不完整观测处理，确保实验结果具有准确的统计含义。最后再扩展 LLM 转换与适用性分析评估。

不建议现阶段重写整个模块，也不建议先增加大量新 Oracle。优先确保已有 Oracle 对正控、负控和边界场景都能给出正确判定，再扩大测试范围。

### 修改完成后的建议验证流程

1. 运行现有单元测试与慢速端到端测试。
2. 为每个 P0 项目增加能复现原问题的回归测试。
3. 对每个 Oracle 分别运行正控与负控。
4. 验证多线程配置确实逐一执行。
5. 验证 `PASS`、`VIOLATION`、`INCONCLUSIVE`、`NOT_APPLICABLE` 的语义和汇总规则。
6. 保存 commit、Harness 哈希、测试配置、随机种子和完整日志。
7. 在修复版本上重跑历史候选，确认不会因修改而丢失已知问题的检出能力。
